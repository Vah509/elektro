# Инструменты проверки

Сверено с исходником `audit-site.mjs` (385 строк, Node 18+, без зависимостей), 2026-10-29. Скрипты лежат у владельца отдельно, в репозиторий не входят; `psi-report-v3.mjs` в чат не приходил — его раздел описан по передаче чатов.

## audit-site.mjs — структурный аудит сайта
```
node audit-site.mjs [BASE_URL] [МЕТКА]
node audit-site.mjs                                           # боевой сайт https://elektroschit.com.ua
node audit-site.mjs http://localhost:4321 local               # локально: npm run build → python3 -m http.server 4321 -d dist
node audit-site.mjs https://<ветка>.elektro-4a1.pages.dev preview
```
Результат: `audit-summary[-МЕТКА].md` и `.json` рядом со скриптом — присылать оба в чат. Время локального прогона ≈ 1–2 минуты.

**Что проверяет**
1. Все страницы из `sitemap.xml` (+ `/ru/vykonani-roboty/`, страница 404, `robots.txt`): код ответа, редиректы, title (предупреждение > 65 симв.), description (предупреждение вне 110–170), canonical (совпадение с путём, слеш, origin), H1, lang, viewport, og:*, JSON-LD (валидность), hreflang, дубли title/description/H1.
2. Все картинки: HTTP-статус, формат (не WebP — предупреждение), вес (> 250 КБ), alt, width/height, loading, srcset/sizes.
3. Внутренние ссылки: битые (🔴) и лишние редиректы (🟡).
4. Карточки портфолио (глубоко): главное фото (srcset, sizes, не lazy, fetchpriority), миниатюры и их `data-src`/caption, массив фото лайтбокса (число совпадает с миниатюрами, все URL отвечают 200), `.em-lightbox-img`, `em-work-lightbox.js`, блок «Схожі роботи».
5. Каталог `/vykonani-roboty/`: карточки, srcset, eager у первых трёх, `data-types`.
6. Продукция (UA и RU): hero-коллаж = 4 фото, галерея = 8, FAQ, ContactBlock, AlsoMake.

**Уровни:** 🔴 ошибка (ломает страницу/ссылку/лайтбокс — исправлять), 🟡 предупреждение, ⚪ инфо. Критерий после любого ZIP: **0 🔴 и 0 🟡**.
Заметка: порог description в аудите шире правила документации (150–160): 110–170 не даёт предупреждения.

**Результаты**
- Боевой сайт после этапа 2б (2026-10-28): 67 страниц, 825 картинок, реальных ошибок 0.
- Чистый клон `main` после чистки репозитория (локальная сборка, 2026-10-29): 67 страниц, 825 картинок (40 МБ), 39 карточек (206 фото), **🔴 0 | 🟡 0 | ⚪ 0**.

## psi-report-v3.mjs — PageSpeed Insights
```
node psi-report-v3.mjs API_KEY https://elektroschit.com.ua prod 3
```
3 прогона на страницу и **медиана** (разброс PSI между прогонами до 20 баллов: каталог 94→75, карточка 63→97). Решения принимать по медиане. Ключ — бесплатный, Google Cloud Console → PageSpeed Insights API. После деплоя ждать несколько минут: сначала отдаётся старая версия.

Что из этого следует:
- Разница между прогонами A и B у нестабильных страниц (до 40 пунктов при тех же трёх запусках внутри прогона) вызвана «задержкой отрисовки» текстового LCP (0,2 с → 1,3 с вместе с render-blocking 110–150 мс), а не изменением сайта. По этим страницам решения по одному замеру не принимать.
- Две карточки и `/pro-nas/` слабы одинаково в обоих прогонах — это реальная проблема. У карточек фото грузится за 0,1–0,2 с, но LCP наступает на ~2 с позже (задержка отрисовки), FCP 3,4–3,6 с против 0,9 с на быстрых страницах.
- Наблюдение по сборке (`dist/`, 2026-10-28): у шаблона карточек есть внешний `<link rel="stylesheet" href="/_astro/_slug_.*.css">` (≈ 8,4 КБ, scoped-стили `[slug].astro` и `WorkPhotos`; Astro выносит CSS больше ~4 КБ в файл). Остальные страницы получают все стили inline. Это совпадает с render-blocking 150 мс на карточках, но у `/pro-nas/` внешнего CSS нет, а блокировка 150 мс есть — **причина не доказана**; для `/pro-nas/` нужна трасса (Lighthouse в DevTools). Гипотеза для проверки: `build.inlineStylesheets: 'always'` в `astro.config.mjs` — проверять замером до/после на карточках.
- «Unused JavaScript» ≈ 138 КиБ на всех страницах (вероятно GTM, не откладывать — теряются конверсии). `/kontakty/`: 371 КиБ и interactive 7,5–7,9 с (вероятно карта).
- Критерий, что страница «хорошая»: оценка ≥ 90 в обоих прогонах.
